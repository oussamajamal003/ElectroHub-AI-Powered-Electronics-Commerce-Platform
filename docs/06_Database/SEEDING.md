# Database Seeding

## 1. Purpose

This document defines the database seeding strategy for ElectroHub.

Seeding provides controlled development and test data for:

- Local development.
- Automated tests.
- Demonstrations.
- QA environments.

Seed data must never contain real customer information or production secrets.

---

# 2. Seed Architecture

```text
Prisma Seed Script
        ↓
Prisma Client
        ↓
Supabase PostgreSQL
```

The seed process should use the same Prisma models as the application.

---

# 3. Seed Environments

Seeding is intended for:

```text
Development
Testing
Demo / QA
```

Production databases must not be reset or populated using destructive development seed logic.

---

# 4. Seed Data Categories

The seed dataset may include:

```text
Users
Categories
Products
Product Images
Inventory
Cart Data where required
Wishlist Data where required
Orders
Order Items
Payments
Deliveries
Recommendations
Behavioral Events
```

Only data required by the environment should be created.

---

# 5. Users

Development users may include:

```text
Customer Account
Administrator Account
```

Example roles:

```text
CUSTOMER
ADMIN
```

Passwords must be securely hashed.

Seed credentials must be development-only.

They must never reuse real user passwords.

---

# 6. Categories

Seed categories should represent the project's electronics catalog.

Examples:

```text
Laptops
Smartphones
Tablets
PC Components
Gaming
Monitors
Networking
Storage
Accessories
Audio
Cameras
Smart Devices
```

The final dataset should remain consistent with the product catalog.

---

# 7. Products

Products should provide enough data to demonstrate:

```text
Catalog
Search
Categories
Recommendations
Cart
Wishlist
Checkout
Inventory
Admin
```

Representative fields include:

```text
Name
Slug
Description
Price
Category
Status
Images
```

Product data should be realistic enough for UI demonstrations but must not use copyrighted or confidential commercial data without permission.

---

# 8. Product Images

Seed products may reference approved Cloudinary/media assets.

The seed script should store image references rather than downloading and storing binary image data in PostgreSQL.

If external image references are used, they must be stable enough for the intended development/demo environment.

---

# 9. Inventory

Each seeded product should have an appropriate inventory record.

The dataset should include examples of:

```text
In Stock
Low Stock
Out of Stock
```

This allows inventory-related UI and tests to be demonstrated.

---

# 10. Orders

Seed orders may demonstrate different lifecycle states:

```text
Confirmed
Preparing
Out for Delivery
Delivered
```

Order items should preserve historical product names and prices.

---

# 11. Payments

Payment seed records must represent test/demo state only.

Examples:

```text
Pending
Succeeded
Failed
```

Stripe provider references should not contain real payment credentials.

The seed data must never simulate real money movement.

---

# 12. Delivery

Seed delivery records may demonstrate:

```text
Confirmed
Preparing
Out for Delivery
Delivered
```

For map demonstrations, controlled test coordinates may be used.

They must not represent real people's locations.

---

# 13. Recommendations

Seed recommendation relationships may demonstrate:

```text
Similar Products
Frequently Bought Together
Popular Products
Category-Based Recommendations
```

If recommendations are dynamically generated by the AI service, static recommendation seed data may be unnecessary.

---

# 14. Behavioral Events

Seed behavioral events may be used to populate analytics dashboards.

Examples:

```text
product.viewed
product.clicked
cart.item_added
wishlist.added
search.performed
image_search.completed
recommendation.clicked
checkout.started
order.created
```

Seed events should clearly represent test/demo behavior.

---

# 15. Idempotent Seeding

The seed process should be designed to avoid accidental duplicate records where practical.

Use stable identifiers or unique fields such as:

```text
email
slug
order_number
```

when appropriate.

The exact strategy depends on whether the seed is:

```text
Reset-and-Rebuild
Upsert-Based
Test Fixture
```

---

# 16. Seed Execution

The project should expose a clear seed command.

Conceptually:

```bash
npx prisma db seed
```

The exact package-script command should be documented in the root/backend configuration.

---

# 17. Development Reset

A destructive reset may be used only for disposable development databases.

Conceptually:

```bash
npx prisma migrate reset
```

This operation must never be executed against a production database.

---

# 18. Seed Ordering

Seed dependencies should be created in a valid order.

Recommended sequence:

```text
1. Users
2. Categories
3. Products
4. Product Images
5. Inventory
6. Cart / Wishlist
7. Orders
8. Order Items
9. Payments
10. Deliveries
11. Recommendations
12. Behavioral Events
13. Notifications / Documents where required
```

Parent records must exist before dependent records are created.

---

# 19. Transactions

Where practical, related seed operations should use database transactions.

For example:

```text
Create Order
 ↓
Create Order Items
 ↓
Create Payment
 ↓
Create Delivery
```

This prevents partially created demo records.

---

# 20. Security

Seed scripts must never contain:

```text
Production Passwords
Stripe Secret Keys
Brevo API Keys
JWT Secrets
Database Passwords
Real Customer Data
```

Secrets must come from environment configuration where genuinely required.

---

# 21. Environment Separation

Seed behavior must be environment-aware.

Recommended separation:

```text
Development Seed
Test Fixtures
Production
```

Production should not automatically execute development seed logic.

---

# 22. Testing

Seed data should support automated tests without making tests dependent on uncontrolled shared state.

Unit/integration tests should preferably create isolated fixtures or use a dedicated test database.

---

# 23. Demo Dataset

The demo dataset should be large enough to demonstrate:

```text
Product Catalog
Search
Filtering
Recommendations
Cart
Wishlist
Checkout
Orders
Inventory
Delivery Tracking
Admin Dashboard
Analytics
```

It should remain small enough for fast local setup.

---

# 24. Definition of Done

Database seeding is complete when:

- Development seed data exists.
- Required categories exist.
- Representative products exist.
- Inventory states are represented.
- Test/demo users exist.
- Example orders exist where required.
- Test payment states exist.
- Delivery examples exist.
- Recommendation data exists where required.
- Analytics demo events exist where required.
- Seed execution is documented.
- Secrets and real customer data are excluded.
- Production cannot be accidentally reset by normal development seeding.
