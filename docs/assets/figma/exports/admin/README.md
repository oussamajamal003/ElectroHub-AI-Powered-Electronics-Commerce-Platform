## 1. Purpose

This directory contains **visual screenshots of the approved ElectroHub component system from Figma Make**.

These screenshots exist to help developers and reviewers reproduce the approved component appearance, states, hierarchy, spacing, and interaction presentation.

They are **visual references**, not production source code.

The objective is:

> **Reproduce the approved ElectroHub component system faithfully. Do not redesign or replace it with an independently invented UI.**

Use these screenshots together with the live Figma Design and the repository's central Figma documentation.

## 6. Screenshot Naming

**No custom component/state naming convention is required.**

Screenshots captured from Figma Make should keep the **default screenshot filename generated by the capture/export process**.

Do not rename screenshots to manually defined names such as:

```text
Button — Default.png
Button — Hover.png
Button — Disabled.png
Input — Default.png
Input — Focus.png
Input — Error.png
```

The repository should preserve the original/default screenshot names so each visual reference remains directly traceable to its source capture.

### Default screenshot names

Use:

```text
<default screenshot filename>.png
```

The actual filename is intentionally not prescribed because it should come from the Figma Make screenshot/export process.

### Responsive references

Responsive screenshots should also keep their **default screenshot filenames**.

Do not require or enforce a naming pattern such as:

```text
<Component> — Desktop.png
<Component> — Tablet.png
<Component> — Mobile.png
```

Instead, the folder organization and documentation should provide the context needed to understand what each screenshot represents.

### Naming rule

```text
Figma Make screenshot
        ↓
Keep default generated filename
        ↓
Place in Components/screenshots/
        ↓
Use documentation/context to identify its component and state
```

**Do not rename, normalize, or invent screenshot filenames unless a specific repository requirement explicitly requires it.**

# 7. Screenshot Capture Policy

These screenshots are intended to represent the approved visual state from **Figma Make**.

When preparing or updating this directory:

### Capture

Capture the component as it appears in the approved Figma Make design.

Preserve:

- Overall composition
- Component dimensions
- Typography
- Colors
- Spacing
- Borders
- Radius
- Icons
- State presentation
- Visible surrounding context when necessary to understand the component

### Do not alter

Do not:

- Redesign the component
- Add personal styling
- Change colors
- Change typography
- Add decorative effects
- Replace icons
- Modify spacing to make it look different
- Create a new visual variant that does not exist in the approved design

The screenshot should document the approved design, not an interpretation of it.

# 8. Relationship to the Live Figma Design

The screenshot package does not replace the live Figma Design.

Use the following decision rule:

```text
Need exact design-system information?
        ↓
Use Figma Design

Need approved Figma Make visual reference?
        ↓
Use component screenshot

Need to validate implementation visually?
        ↓
Compare implementation against
Figma Design + applicable screenshot
```

If the screenshot and live Design appear different, do not automatically assume the screenshot is correct.

Investigate whether the difference represents:

- A different state
- A different viewport
- A later design revision
- An older screenshot
- A visual artifact
- An implementation difference

Document meaningful unresolved conflicts.

# 9. Component Implementation Rules

When implementing a component represented here:

1. Check the live Figma Design.
2. Check the relevant screenshot.
3. Identify the component's intended state.
4. Reuse the approved design tokens.
5. Reuse the approved component system where possible.
6. Preserve responsive behavior.
7. Preserve accessibility-related visual states.
8. Compare the implementation against the reference.
9. Fix visual deviations before considering the component complete.

### Do not create duplicate components

If the project already has an approved shared component, do not create a visually different duplicate merely because a screen needs a similar control.

Prefer:

```text
Shared component
      ↓
Approved variant/state
      ↓
Screen usage
```

instead of:

```text
Screen-specific duplicate
      ↓
Different styling
```

# 12. Accessibility Reference

The component screenshots can visually demonstrate accessibility-related states, but screenshots alone are not sufficient to define accessibility behavior.

Implementation must also follow the approved project accessibility rules.

Important visual requirements include:

- Visible keyboard focus
- Clear disabled states
- Readable text
- Sufficient visual distinction between states
- Clear error presentation
- Clear selected/checked states
- Appropriate icon labeling where applicable

Do not remove focus indicators simply because the reference screenshot does not capture keyboard focus.

# 15. Evidence Rules

A screenshot can establish visual evidence for what is visibly present.

It does **not** automatically prove:

- Hidden interaction logic
- Accessibility semantics
- API behavior
- Component implementation architecture
- Responsive breakpoints not visible in the screenshot
- Exact token definitions
- Unshown component variants

For those details, use the appropriate Figma Design information or project documentation.

If something cannot be verified:

```text
NOT VERIFIED
```

Do not fabricate missing information.

# 16. Make Screenshot vs Production Code

The screenshots are references only.

Production implementation must use the project's approved stack and architecture.

Do not copy Figma Make source code into production merely because it exists.

The repository's frontend architecture remains responsible for:

- React
- TypeScript
- Approved component structure
- State management
- API integration
- Accessibility
- Testing
- Performance
- Maintainability

The screenshot answers:

> **What should this component look like?**

The production implementation answers:

> **How should this component work within ElectroHub?**

Both must align with the approved design.

# 17. No-Redesign Rule

The component screenshot package must never become an excuse to create a replacement design.

Do not:

- Redesign existing components
- Introduce unrelated UI libraries visually
- Change the established design language
- Replace Poppins with another UI font
- Replace JetBrains Mono for data UI
- Introduce arbitrary colors
- Introduce arbitrary radius values
- Remove approved states
- Change component hierarchy without evidence
- Create screen-specific styling that contradicts the shared component system

If the design is unclear:

```text
VERIFY FIRST.
DO NOT INVENT.
```

# 18. Updating Screenshots

When the approved Figma Design changes:

1. Identify affected components.
2. Verify whether the change is intentional.
3. Update the relevant screenshot reference if necessary.
4. Keep filenames stable when the referenced component/state remains the same.
5. Remove obsolete screenshots only when their design is no longer approved.
6. Update this README if the component inventory or structure changes.
7. Re-run visual QA against affected frontend components.

Avoid keeping contradictory screenshots without documenting which version is approved.

---

# 19. Review Guidance

A reviewer should ask:

### Design fidelity

- Does the implementation match the approved component?
- Are tokens reused correctly?
- Are states represented correctly?
- Is responsive behavior preserved?

### Architecture

- Is the component shared rather than duplicated?
- Does it belong in the correct component tier?
- Does it follow the existing frontend architecture?

### Accessibility

- Is keyboard focus preserved?
- Are states distinguishable?
- Are interactive controls accessible?

### Regression

- Did the change alter another screen using the same component?
- Did responsive behavior regress?
- Did an existing component variant change unintentionally?
