# Profile Photos and Administrator Authentication Background

## Scope

This change adds a private profile-photo feature for authenticated customers and MFA-assured administrators, and uses an original ElectroHub blue/cyan electronics image behind the shared administrator authentication layout. The shared layout covers login (including inline MFA, OTP and passkey challenges), recovery, activation and invitation acceptance. The white authentication card stays opaque so existing controls retain their contrast in light and dark system themes.

## Photo API and storage

| Role | Read | Upload | Remove |
| --- | --- | --- | --- |
| Customer | `GET /api/account/profile-photo` | `POST /api/account/profile-photo` | `DELETE /api/account/profile-photo` |
| Administrator | `GET /api/admin/me/profile-photo` | `POST /api/admin/me/profile-photo` | `DELETE /api/admin/me/profile-photo` |

Uploads use one multipart `photo` field. The API authenticates and role-checks before reading the multipart body. It accepts JPEG, PNG or WebP input up to 5 MiB; Sharp checks/decodes the image, applies orientation, limits input pixels, crops/resizes to 512×512, strips source metadata and stores normalized WebP. The UI also offers browser camera capture and a device-file fallback. A failed or cancelled camera request does not block photo selection.

The database stores only the private Storage object path in nullable `users.profile_photo_path`. Paths are generated by the server under `customers/<authenticated-user-id>/` or `admins/<authenticated-user-id>/`. Customers and admins use separate routes and query-cache keys. Read endpoints return a signed URL limited to 30 minutes and set `Cache-Control: private, no-store`; the frontend refreshes active photo URLs before expiry. Supabase credentials remain on the backend. Uploads are limited to 12 writes per user per hour and two concurrent photo-processing requests per API process.

The additive Prisma migration provisions or validates a private `profile-photos` Supabase bucket restricted to `image/webp` and 5 MiB. It skips bucket DML on plain PostgreSQL installations without Supabase Storage. The migration must be applied through the repository's normal reviewed database release process. No shared DEV or PROD storage/database was modified as part of this task.

## Security and lifecycle

- A profile path is checked against the authenticated user ID and role before it is read or deleted.
- Upload uses server-generated UUID paths and no upsert; the stored image bytes are re-encoded before reaching Storage.
- Concurrent replacements use an optimistic database condition on the prior path and clean up their losing newly uploaded object.
- If cleanup of the replaced image fails, the previous private object can remain orphaned. The user association still points only to the new photo; cleanup failure is logged without exposing credentials or image bytes.
- Account deletion and admin account deletion do not yet include a dedicated orphan cleanup job for profile-photo objects. The bucket stays private, so such an orphan is not publicly readable; operational cleanup can be added with an approved retention process.
- External Supabase behavior is covered with adapter tests; live Storage upload/sign/delete is not performed during local verification to avoid mutating shared data.
