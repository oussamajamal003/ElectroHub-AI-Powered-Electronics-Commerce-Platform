# Customer Product Catalog

The customer `/products` page is the catalog discovery surface. It renders the shared compact SearchField, product grid, category/brand/availability/price filters, sort, active-filter removal, reset, and pagination.

Catalog search and the dedicated `/search` page share `GET /api/search/products`, `GET /api/search/suggestions`, SearchService, canonical Product Foundation summaries, and URL-backed query/filter state. An initial `/products` visit loads a bounded newest-first page through the empty-query API contract; plain `/search` intentionally remains empty until a query or filter is active. Query input updates after a 275 ms debounce; query edits replace the URL entry, while deliberate filter/sort/page actions remain navigable.

Filter controls use live Category and Brand API data. The price range is applied as one filter. An empty query requests only a bounded, newest-first page and its total count; it never materializes the entire catalog. Product prices are display-only adapters of the API's decimal strings; the client does no commerce arithmetic.

The global customer Footer is rendered once by CustomerLayout, not per page. Its approved content and responsive layout follow `docs/assets/figma/exports/customer/screenshots/Footer.png`; Admin and standalone authentication layouts do not receive it.

## Task 03.1 catalog extension

Home reads bounded newest-first Products, active Categories with grouped active-Product counts, and a bounded deals endpoint. Its customer order is Hero, three-column benefits, Categories, Deals, promotions, then New Arrivals. Section queries use content-shaped skeletons and compact retry panels while retaining cached data during background fetches. `/products/:slug` reads Product detail, ordered images and grouped specifications, plus a separately paginated Review list. “More in Category” reuses the existing Search endpoint; it is not an AI recommendation. Product and Search summaries expose `averageRating` (one-decimal string or null), `reviewCount`, and Decimal-derived `discountPercent` without returning Review rows or full specifications. Search listings use one parameterized, page-bounded SQL statement for the total, ordered page, two preview images per Product, and grouped Review ratings; no Review rows or full specifications are returned. ProductCard hover uses those fetched images without another request.

Review reads are public for visible Products. Review creation/update/deletion requires an authenticated customer; Product and User identity are resolved server-side. A customer may have at most one Review per Product. Rating is 1–5 and trimmed body is 1–2,000 characters. Public Review responses contain a display name, never email or internal User fields. Account-deletion tombstones display as “Deleted Customer.” Review guest UI waits for AuthContext initialization. Review-list responses include the current rating summary; create/update responses return the saved Review and new summary. The client patches the own-Review, visible Review-page, Product-detail summary, Product-list, and Search caches. Delete retains HTTP 204, refreshes one bounded Review page for the new aggregate, and invalidates only Product lists/deals and Search results; it never invalidates the Product-detail payload, so the gallery and specifications remain mounted. The backend remains authoritative for ownership and availability.

The authenticated `GET /api/reviews/me` returns a bounded review history for the current customer only, including visible Product name, slug, and primary image. Account links open that Product’s Review tab using the `#reviews` fragment. The current customer’s own public-list entry is labeled “Your review” rather than exposing their personal name.

The additive `20260928000000_product_reviews` migration adds the Review table, foreign keys, unique ownership key, pagination/look-up indexes, and database rating/body checks. The migration must be applied through the separate DEV/PROD database gate before Review reads or writes can work against live data. The expanded DEV-only seed is guarded against a non-DEV target and uses stable upserts for 128 curated Products and 320 Reviews from inactive `.invalid` synthetic reviewers. Existing legacy Products are retained; no production seed is permitted. Every curated Product has at least two distinct local ProductImage records. Smartphone media are brand-aware illustrative views rather than alternated across Apple and Samsung; the reviewed seed code still requires Gemini's DEV rerun before live rows reflect this change. No media needs a runtime hotlink.

Fresh direct entry and refresh start at the top. First-time SPA PUSH routes start at the top, previously visited route identities restore their saved position, and Back/Forward restores the exact in-session history-entry position. Catalog ProductCard navigation remains within the router and preserves Query cache. Guest Orders renders a sign-in-required card without exposing orders, and the customer header omits the Account text link until authentication resolves. Account Settings links to the existing `/account/profile` route. Product image pools use deterministic category-specific local JPEG variants (three generated views for each catalog category); smartphone seed images use distinct Apple-style and Samsung-style pools. ProductCard hover transitions use the already-fetched alternate image and issue no Product or hover-specific API request.

The Category list uses the same bounded RepeatableRead transaction wait/timeout as Product and Search reads. This prevents the default short interactive-transaction timeout from surfacing intermittent 500s when the remote DEV connection is slow; it does not change Category response data or matching.
