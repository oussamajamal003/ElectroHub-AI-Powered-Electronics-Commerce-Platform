The build job stops before checkout, image creation, bundle packaging, or artifact upload. The deploy job stops before artifact download, runner-side `docker load`, SSH setup, transfer, or host invocation.\n- The workflow still packages five individual files rather than one complete immutable payload with a single attested digest. It has no `actions/attest` step and no OIDC/attestation write permissions. The current internal release manifest and its SHA-256 entries prove only consistency among files; they do not authenticate their origin.\n- `infrastructure/production/prepare-release-bundle.py` calls `_require_approved_release_provenance()` before host configuration or intake. The helper's prepare CLI does the same. This remains the active host-side hold.\n- The SSH transfer and old bundle manifest are not an authenticated release envelope. The fixed host helper does not yet verify Sigstore evidence, root freshness, repository ID, exact workflow identity, release/run/attempt identity, deployment environment, or replay state.\n\n### Fixed production environment and AI checks\n\n`infrastructure/production/verify-production-env.py` already checks the production target, same-origin HTTPS settings, secret strength, worker-disabled settings, DB project identity/TLS, and Stripe Test Mode constraints. `apps/ai-service/verify-model-artifact.py --production` already checks the host-pinned AI release manifest, approval references, model/relevance/preprocessing identity and configured artifact bytes.\n\nThe deployment installer previously installed only the deployment script and bundle helper, and the deployment script did not invoke these validators. The installer now installs both validators to fixed `/usr/local/libexec` paths as root-owned files with restrictive `0640` modes. `deploy-release.sh` verifies their ownership and that they are not group/world-writable, then invokes environment validation and AI production metadata/artifact validation before Compose configuration validation, Docker image load, release installation, active-pointer change, or service startup. The separate application provenance gate remains earlier and unconditional.\n\nThese fixed checks do not establish application provenance and do not approve AI quality, artifact source, redistribution rights, vector-index compatibility/activation, or a production model release. The AI source, rights, and D3 quality blockers recorded by Task 06.3F remain binding.\n\n## Approved direction and proposed verification contract\n\nThe owner-approved direction for implementation is GitHub artifact attestations using GitHub OIDC and Sigstore, with repository ID `1329865493`, an independently managed host trust root, fail-closed verification, replay prevention, and application-provenance/AI-approval separation. The numeric ID is treated as owner-provided approval; it was not independently queried from GitHub during this task.\n\nThe release payload must become one immutable archive containing the source archive, image archive, internal release manifest and AI approval metadata. The workflow must compute and attest the SHA-256 digest of that complete archive, and transfer that exact archive plus the attestation bundle. Host verification must use a fixed, root-owned verifier and a trust root provisioned independently from SSH intake. The bundle's own manifest remains an integrity check only.\n\nBefore any bundle extraction or use, a fixed host verifier must establish the cryptographic attestation and compare verified certificate/provenance evidence with root-managed policy for:\n\n- repository ID `1329865493` and canonical repository identity;\n- exact signer workflow identity/path and trusted OIDC issuer;\n- protected ref and approved GitHub Environment;\n- source commit SHA and complete bundle digest;\n- unique release identity, workflow run ID and attempt;\n- intended production environment and one-time deployment authorization.\n\nThe host must reject missing, malformed, invalid, stale, mismatched or replayed evidence before extraction, bundle code execution, Docker load, pointer mutation, or Compose. A verifier, trust root, replay ledger, authorization record, or network dependency failure remains a hard rejection. A checksum manifest cannot substitute for attestation.\n\nGitHub's offline-verification guidance confirms that the host must compare the certificate's repository ID for a bundle received outside the GitHub attestation API; offline repository-name matching alone is insufficient. GitHub's CLI exposes verified certificate/timestamp data separately from statement predicate fields, which may be workflow-controlled. A dedicated trusted-builder workflow therefore remains the recommended pattern, subject to exact owner approval and protection controls. [Offline verification guidance](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline), [GitHub CLI attestation verification](https://cli.github.com/manual/gh_attestation_verify), [GitHub OIDC claim reference](https://docs.github.com/en/actions/reference/security/oidc).\n\n## Signer workflow and account configuration\n\nThe present workflow is named `Single-origin production release and deploy`, on `develop`, with deployment job Environment `electrohub-production-deploy`.
